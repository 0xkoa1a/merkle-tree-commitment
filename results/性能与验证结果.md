# 性能与验证结果

本次结果来自整理后的最终 baseline。32 B 消息下，耗时主要由 Keccak 置换次数决定：补齐容量 $N$ 不变时，建树时间基本不变；跨过二次幂边界后，$N$、置换次数和建树时间同时接近翻倍。单项证明则只随树深度缓慢增长。

## 测量条件

- 时间：2026-10-12 18:21:41（Asia/Shanghai）。
- Python 3.9.6，macOS 26.6.2，arm64。
- 源码提交：`e7694fd23d2d3d43d20f4bd216319a17723c7d20`；测量时工作树包含本轮尚未提交的整理改动。
- 每项先预热一次，再采集 5 组样本；表中为均值 ± 样本标准差。
- 建树包含消息转换、独立 nonce 生成、哈希和树节点保存。
- 单项验证输入使用编码后的承诺和证明，因此计时包含解析。

原始样本与环境字段见 [results.json](results.json)。

## 建树、完整验证和逻辑存储

每条消息固定为 32 B。当前补齐树共有 $N$ 个叶位置，建树需要 $2N$ 次哈希；这些输入在本组样本中都只需一次 Keccak 置换，因此哈希调用数与置换次数相同。逻辑存储只计算摘要、nonce 和消息本身：

$$
(2N-1)\cdot32+32n+\sum_i|m_i|\ \text{B}.
$$

`n=256→257`、`512→513`、`1024→1025` 时补齐容量翻倍，建树时间也接近翻倍；而 `n=257` 与 `512`、`513` 与 `1024` 的容量相同，时间基本一致。这说明当前性能由补齐后的节点数主导，而不只由真实消息数主导。

## SHA3-256 的块边界

SHA3-256 的 rate 为 136 B，置换次数为 $\lfloor\ell/136\rfloor+1$。输入从 135 B 增加到 136 B 时需要额外填充块，耗时随置换次数近似成比例增长。

| 32 | 1 | 0.619 ± 0.010 |
| 135 | 1 | 0.609 ± 0.003 |
| 136 | 2 | 1.229 ± 0.013 |
| 137 | 2 | 1.233 ± 0.010 |
| 273 | 3 | 1.844 ± 0.019 |
| 4,096 | 31 | 18.261 ± 0.387 |

## 消息长度边界

真实叶哈希除消息外还有 57 B 固定输入，所以消息不超过 78 B 时只需一次置换，79 B 时开始需要两次。这里固定 $n=32$。

| 每条消息 B | 建树 ms |
| ---: | ---: |
| 0 | 36.901 ± 0.165 |
| 32 | 37.431 ± 0.222 |
| 78 | 37.592 ± 0.038 |
| 79 | 56.534 ± 0.161 |
| 4,096 | 595.016 ± 2.783 |

从 78 B 到 79 B 时，只有 32 个真实叶的置换数增加，内部节点和最终承诺不变，所以总建树时间增加约一半而不是翻倍。4096 B 消息由叶哈希吸收成本主导。

## 结论边界

这些数据用于验证当前纯 Python 实现的成本模型，不构成对其他语言、硬件或哈希实现的通用性能结论。当前 baseline 的主要瓶颈是手写 Keccak 置换；后续 Multiproof 的比较应优先统计兄弟摘要数、验证哈希数和置换数，只在少量代表点计时确认。
